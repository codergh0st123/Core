# Техническая конфигурация Core

Этот документ описывает параметры, добавленные для управляемой нагрузки, сетевой синхронизации и sidebar scoreboard. Все пользовательские ключи в `config.yml` записываются в **ВЕРХНЕМ РЕГИСТРЕ**.

## Скрытие системных сообщений

Параметры `MESSAGES.HIDE` действуют глобально и не зависят от мира игрока. Скрытие не отменяет вход игрока, выход игрока или выдачу достижения — оно изменяет только серверное сообщение для чата.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `MESSAGES.HIDE.ADVANCEMENTS` | `true` | Отключает игровое правило `announceAdvancements` во всех уже загруженных и новых мирах. |
| `MESSAGES.HIDE.JOIN` | `true` | Скрывает стандартное сообщение о входе. |
| `MESSAGES.HIDE.QUIT` | `true` | Скрывает стандартное сообщение о выходе. |

Изменение `ADVANCEMENTS` на `false` прекращает управление правилом Core, но намеренно не меняет игровое правило обратно автоматически. Если нужно снова показывать достижения, включите `announceAdvancements` через стандартную команду gamerule в нужных мирах.

## Очистка выброшенных предметов

Модуль `ITEM-CLEANER` проверяет только сущности типа `Item` во всех загруженных мирах. Он не удаляет мобов, опыт, стрелы, стойки для брони или предметы в инвентарях. Очистка начинается лишь когда количество выброшенных предметов достигает заданного порога; перед удалением игроки получают сообщения из конфигурации. Задача полностью отменяется при выключении плагина и пересоздаётся при `/core reload`.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `ITEM-CLEANER.ENABLED` | `true` | Включает плановую очистку. |
| `ITEM-CLEANER.CHECK-INTERVAL` | `300` | Период проверки количества предметов в секундах. Минимум — `1`. |
| `ITEM-CLEANER.MINIMUM-ITEMS` | `50` | Минимальное число выброшенных предметов для запуска отсчёта. |
| `ITEM-CLEANER.CLEAR-DELAY` | `30` | Длительность отсчёта до удаления в секундах. `0` запускает очистку сразу после проверки. |
| `ITEM-CLEANER.WARNING-SECONDS` | `30`, `10`, `5` | Значения отсчёта, на которых отправляется предупреждение. |
| `ITEM-CLEANER.MESSAGES.WARNING` | список | Сообщение перед очисткой. Поддерживает `&`, `&#RRGGBB`, `&x`, градиенты, PlaceholderAPI и `%SECONDS%`. |
| `ITEM-CLEANER.MESSAGES.CLEARED` | список | Сообщение после очистки. Поддерживает те же форматы и `%COUNT%` — число удалённых предметов. |

Все сообщения остаются списками с `-`, как и остальные сообщения Core. Для уже существующего `config.yml` скопируйте секцию `ITEM-CLEANER` из новой стандартной конфигурации, затем выполните `/core reload`.

## Отладочные интеграции

Команда `/log on` включает персональный вывод отладочных событий в чат администратора, а `/log off` отключает его. Команда требует `core.log` и работает только для игрока. Подписка хранит UUID, удаляется при выходе игрока, при `/core reload` не изменяется и полностью очищается при выключении Core. Обычные игроки эти сообщения не получают.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DEBUG.ENABLED` | `true` | Включает приём отладочных событий Core API. |
| `DEBUG.SOURCES.DONATIONALERTS` | `true` | Показывает успешные выдачи покупок DonationAlerts. |
| `DEBUG.SOURCES.FREESYSTEM` | `true` | Показывает успешные выдачи наград FreeSystem. |
| `DEBUG.SOURCES.DONATEPOINTS` | `true` | Показывает операции добавления, установки, списания и перевода DonatePoints. |

Core предоставляет статический API `ru.core.api.CoreDebug`. Внешний плагин вызывает `CoreDebug.log("SOURCE", "message")`; Core безопасно переводит отправку в основной поток и доставляет её только администраторам, включившим `/log on`. Если Core отключён, отсутствует или в нём нет активных подписчиков, вызов ничего не делает и не создаёт задачу. DonationAlerts, FreeSystem и DonatePoints используют лёгкий мост к этому API без включения Core-классов в свои JAR.

## Группы LuckPerms в Tab

Core читает `groups.yml` и получает **primary group** уже загруженного пользователя LuckPerms. Для каждой группы можно задать формат имени в tab-list. LuckPerms является мягкой зависимостью: при его отсутствии Core не выполняет запросов к базе данных, не сохраняет старые состояния tab-list и продолжает работать без групповой сортировки.

| Ключ | Назначение |
|---|---|
| `TAB-PREFIX` | Текст перед именем игрока в tab-list. |
| `TAB-SUFFIX` | Текст после имени игрока в tab-list. |
| `TAG-PREFIX` | Текст перед ником игрока над головой. |
| `TAG-SUFFIX` | Текст после ника игрока над головой. |

Порядок задаётся в `TAB.SORTING_TYPES`. Запись `GROUPS:owner,admin,default` задаёт приоритет групп слева направо. `PLACEHOLDER_A_TO_Z:%player%` добавляет буквенный порядок внутри каждой группы. Core использует штатный `Player#setPlayerListOrder`, поэтому не создаёт scoreboard-команды и не использует NMS для сортировки.

`groups.yml` поддерживает `%CORE_ANIMATION:OWNER%`, `&`, `§`, `&#RRGGBB`, `&x` и любые расширения PlaceholderAPI. Поля `%vault_prefix%`, `%vault_suffix%` и `%vault_ranksuffix%` в стандартном примере требуют установленный PlaceholderAPI и соответствующее Vault-расширение. Надголовные теги включаются ключом `NAMETAG.GROUPS.ENABLED` и обновляются только при изменении группы или её форматированного текста; в каждом персональном scoreboard создаётся не более одной команды на группу. После изменения `groups.yml`, `TAB.SORTING_TYPES` или группы игрока выполните `/core reload`.

## Текстовые анимации

Core загружает `animations.yml` при запуске и при `/core reload`. В корне файла каждая секция является именем анимации. Название не зависит от регистра, но пользовательские YAML-ключи в примерах и файле по умолчанию записываются в **ВЕРХНЕМ РЕГИСТРЕ**.

| Ключ | Назначение |
|---|---|
| `CHANGE-INTERVAL` | Период смены кадра в миллисекундах. Минимальное значение — `1`. |
| `TEXTS` | Непустой список кадров анимации. Поддерживаются `§`, `&`, `&#RRGGBB`, `&x` и градиенты Core. |

Чтобы вывести анимацию в конфигурациях Core, используйте `%CORE_ANIMATION:OWNER%`. При установленном PlaceholderAPI аналогичный плейсхолдер имеет вид `%core_animation:owner%`. Неизвестное имя остаётся без подстановки, поэтому ошибки конфигурации не заменяются пустым текстом.

Анимации используют монотонное время и не запускают отдельную задачу на каждый кадр или игрока. Это не создаёт фоновых задач и не удерживает игроков в памяти. Изменения в `animations.yml` применяются командой `/core reload`.

## ProtocolLib: подавление дублирующихся пакетов

Интеграция ProtocolLib является **опциональной**. Core использует её только если ProtocolLib установлен и включён на сервере. Фильтр рассматривает только исходящие `SCOREBOARD_OBJECTIVE`, `SCOREBOARD_TEAM` и `SCOREBOARD_SCORE`, относящиеся к ресурсам Core с идентификатором `CORE_`. Он отменяет лишь подряд идущие идентичные пакеты в заданном коротком окне; пакеты других плагинов не анализируются и не изменяются.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `PROTOCOLLIB.ENABLED` | `true` | Включает интеграцию, если ProtocolLib доступен. |
| `PROTOCOLLIB.DUPLICATE-WINDOW-MILLIS` | `100` | Окно в миллисекундах для отмены ближайшего идентичного пакета. `0` отключает фильтрацию. |

Core также не отправляет неизменный header/footer tab-листа повторно. Состояния фильтра ProtocolLib и tab-кэша удаляются при выходе игрока и полностью очищаются при `/core reload` или выключении плагина.

## Scoreboard

Sidebar обновляется пакетами игроков, а не одним тяжёлым проходом по всему онлайну. Благодаря этому нагрузка на основной поток распределяется равномерно. Параметр `PLAYERS-PER-UPDATE` задаёт количество игроков, чьи строки обновляются за один запуск задачи.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `SCOREBOARD.ENABLED` | `true` | Включает или выключает sidebar. |
| `SCOREBOARD.UPDATE` | `20` | Период запуска обновления в тиках. |
| `SCOREBOARD.NUMBERS.HIDDEN` | `true` | Убирает числовые значения справа от строк sidebar. |
| `SCOREBOARD.PERFORMANCE.PLAYERS-PER-UPDATE` | `100` | Лимит игроков, обновляемых за один запуск задачи. |

> Для фактического скрытия чисел справа требуется **Paper 1.20.3+**. На чистом Spigot Core продолжает работать без ошибок, но сервер не предоставляет API для скрытия этих чисел, поэтому они останутся видимыми.

Для 100–300 игроков начните со значения `100`. Для 500–1000 игроков используйте `100`–`200` и повышайте значение только если сервер сохраняет стабильный TPS. При `100` игроках на обновление и `UPDATE: 20` полный проход по 1000 онлайн-игрокам занимает примерно 10 секунд, без одного тяжёлого пика в основном потоке.

## Сетевая синхронизация MySQL

Сетевые сообщения используются только в режиме `DATABASE.TYPE: MYSQL`. Обработчик синхронизации читает сообщения по порядковому ID, ограничивает размер одной выборки, а при `/core reload` отменяет устаревшие фоновые результаты. Это предотвращает доставку сообщений из предыдущей сессии после перезагрузки.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.SYNC-INTERVAL` | `40` | Интервал опроса синхронизации в тиках. |
| `DATABASE.SYNC.MESSAGES-PER-POLL` | `100` | Максимальное число сообщений, читаемых за один SQL-опрос. Допустимый диапазон в коде: `1`–`1000`. |
| `DATABASE.SYNC.CLEANUP-EVERY-POLLS` | `50` | Через сколько опросов очищать устаревшие сообщения. |
| `DATABASE.SYNC.RETENTION-SECONDS` | `120` | Срок хранения сетевых сообщений в секундах; минимум `60`. |

Большой backlog обрабатывается частями. Не повышайте `MESSAGES-PER-POLL` выше необходимого: это увеличивает время SQL-операции и число сообщений, доставляемых за один основной тик.

## Сохранение профилей

`DATABASE.SAVE-INTERVAL` задаёт период регулярного сохранения данных игроков в секундах. Core сохраняет онлайн-профили одной SQL-транзакцией с `batch`-операцией и выполняет rollback при ошибке. Это уменьшает число коммитов при высоком онлайне и не оставляет соединение в режиме отключённого auto-commit.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.SAVE-INTERVAL` | `300` | Период пакетного сохранения онлайн-профилей в секундах. Минимум `30`. |

## Кэш недавно отключившихся игроков

Core удерживает только ограниченное число уже сохранённых профилей недавно отключившихся игроков. Повторный вход в пределах TTL не требует новой SQL-загрузки. Кэш не хранит онлайн-профили дополнительно, очищается по таймеру, ограничивается LRU-лимитом и полностью освобождается при выключении плагина. Профиль сначала ставится на асинхронное сохранение, а затем может попасть в кэш, поэтому кэш не является единственной копией данных.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.CACHE.ENABLED` | `true` | Включает кэш недавно отключившихся игроков. |
| `DATABASE.CACHE.MAX-ENTRIES` | `250` | Максимум профилей в памяти. При превышении удаляется самая давно неиспользуемая запись. |
| `DATABASE.CACHE.TTL-SECONDS` | `300` | Время жизни записи после выхода игрока в секундах. Минимум в коде: `30`. |
| `DATABASE.CACHE.CLEANUP-INTERVAL` | `60` | Интервал очистки истёкших записей в секундах. Минимум в коде: `15`. |

Для серверов с 100–1000 онлайна начальные значения `250` и `300` секунд безопасны: память кэша ограничена, а частые переподключения не создают лишнюю нагрузку на SQL. Если быстрый повторный вход не важен, установите `DATABASE.CACHE.ENABLED: false`.

Изменения всех параметров из этого документа применяются через `/core reload`. Перезагрузка корректно обновляет `animations.yml` и `groups.yml`, отменяет и создаёт заново задачи интерфейса, ProtocolLib-фильтра, синхронизации, автосохранения и кэша; загруженные профили и SQL-соединение при этом не теряются.

## Синхронизированный стафф-чат

Команда `/schat <сообщение>` доставляет текст игрокам с правом `core.chat.staff` на текущем сервере и публикует событие в таблицу `CORE_NETWORK`. Каждое другое ядро Core читает эту таблицу отдельной фоновой очередью и передаёт готовое сообщение в основной поток Bukkit только для вывода в чат.

Для синхронизации между серверами требуются `DATABASE.TYPE: "MYSQL"`, одна общая база данных и уникальный ключ `SERVER` в `config.yml` у каждого сервера. SQLite сохраняет локальную работу `/schat`, но не синхронизирует сообщения между серверами.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.SYNC-INTERVAL` | `20` | Частота асинхронной проверки сетевых сообщений в тиках. |
| `DATABASE.SYNC.MESSAGES-PER-POLL` | `250` | Максимальный размер одного пакета чтения. |
| `DATABASE.SYNC.CLEANUP-EVERY-POLLS` | `300` | Количество проверок до фоновой очистки устаревших записей. |
| `DATABASE.SYNC.RETENTION-SECONDS` | `300` | Хранение сообщений в секундах; минимально `60`. |

Публикация, чтение и очистка сетевой шины выполняются в отдельной последовательной очереди `Core-Network`. Она не конкурирует с загрузкой профилей, сохранением игроков и их batch-операциями в `Core-Storage`. Это исключает блокировку основного потока и сохраняет упорядоченную доставку сообщений при высоком онлайне.
