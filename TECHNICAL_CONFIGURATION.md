# Техническая конфигурация Core

Этот документ описывает параметры, добавленные для управляемой нагрузки, сетевой синхронизации и sidebar scoreboard. Все пользовательские ключи в `config.yml` записываются в **ВЕРХНЕМ РЕГИСТРЕ**.

## Scoreboard

Sidebar обновляется пакетами игроков, а не одним тяжёлым проходом по всему онлайну. Благодаря этому нагрузка на основной поток распределяется равномерно. Параметр `PLAYERS-PER-UPDATE` задаёт количество игроков, чьи строки обновляются за один запуск задачи.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `SCOREBOARD.ENABLED` | `true` | Включает или выключает sidebar. |
| `SCOREBOARD.UPDATE` | `20` | Период запуска обновления в тиках. |
| `SCOREBOARD.NUMBERS.HIDDEN` | `true` | Убирает числовые значения справа от строк sidebar. |
| `SCOREBOARD.PERFORMANCE.PLAYERS-PER-UPDATE` | `100` | Лимит игроков, обновляемых за один запуск задачи. |

> Для фактического скрытия чисел справа требуется **Paper 1.20.3+**. На чистом Spigot Core продолжает работать без ошибок, но сервер не предоставляет API для скрытия этих чисел, поэтому они останутся видимыми.

Для 100–300 игроков начните со значения `100`. Для 500–1000 игроков используйте `100`–`200` и повышайте значение только если сервер сохраняет стабильный TPS. При `100` игроках на обновление и `UPDATE: 20` полный проход по 1000 онлайн-игрокам занимает примерно 10 секунд, без одного тяжёлого пика в основном потоке.

## Сетевая синхронизация MySQL

Сетевые сообщения используются только в режиме `DATABASE.TYPE: MYSQL`. Обработчик синхронизации читает сообщения по порядковому ID, ограничивает размер одной выборки, а при `/core reload` отменяет устаревшие фоновые результаты. Это предотвращает доставку сообщений из предыдущей сессии после перезагрузки.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.SYNC-INTERVAL` | `40` | Интервал опроса синхронизации в тиках. |
| `DATABASE.SYNC.MESSAGES-PER-POLL` | `100` | Максимальное число сообщений, читаемых за один SQL-опрос. Допустимый диапазон в коде: `1`–`1000`. |
| `DATABASE.SYNC.CLEANUP-EVERY-POLLS` | `50` | Через сколько опросов очищать устаревшие сообщения. |
| `DATABASE.SYNC.RETENTION-SECONDS` | `120` | Срок хранения сетевых сообщений в секундах; минимум `60`. |

Большой backlog обрабатывается частями. Не повышайте `MESSAGES-PER-POLL` выше необходимого: это увеличивает время SQL-операции и число сообщений, доставляемых за один основной тик.

## Сохранение профилей

`DATABASE.SAVE-INTERVAL` задаёт период регулярного сохранения данных игроков в секундах. Core сохраняет онлайн-профили одной SQL-транзакцией с `batch`-операцией и выполняет rollback при ошибке. Это уменьшает число коммитов при высоком онлайне и не оставляет соединение в режиме отключённого auto-commit.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.SAVE-INTERVAL` | `300` | Период пакетного сохранения онлайн-профилей в секундах. Минимум `30`. |

## Кэш недавно отключившихся игроков

Core удерживает только ограниченное число уже сохранённых профилей недавно отключившихся игроков. Повторный вход в пределах TTL не требует новой SQL-загрузки. Кэш не хранит онлайн-профили дополнительно, очищается по таймеру, ограничивается LRU-лимитом и полностью освобождается при выключении плагина. Профиль сначала ставится на асинхронное сохранение, а затем может попасть в кэш, поэтому кэш не является единственной копией данных.

| Ключ | Значение по умолчанию | Назначение |
|---|---:|---|
| `DATABASE.CACHE.ENABLED` | `true` | Включает кэш недавно отключившихся игроков. |
| `DATABASE.CACHE.MAX-ENTRIES` | `250` | Максимум профилей в памяти. При превышении удаляется самая давно неиспользуемая запись. |
| `DATABASE.CACHE.TTL-SECONDS` | `300` | Время жизни записи после выхода игрока в секундах. Минимум в коде: `30`. |
| `DATABASE.CACHE.CLEANUP-INTERVAL` | `60` | Интервал очистки истёкших записей в секундах. Минимум в коде: `15`. |

Для серверов с 100–1000 онлайна начальные значения `250` и `300` секунд безопасны: память кэша ограничена, а частые переподключения не создают лишнюю нагрузку на SQL. Если быстрый повторный вход не важен, установите `DATABASE.CACHE.ENABLED: false`.

Изменения всех параметров из этого документа применяются через `/core reload`. Перезагрузка корректно отменяет и создаёт заново задачи интерфейса, синхронизации, автосохранения и кэша; загруженные профили и SQL-соединение при этом не теряются.
